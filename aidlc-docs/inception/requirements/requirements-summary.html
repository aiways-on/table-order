🍽️ 테이블오더 서비스 — 요구사항 요약

AI-DLC INCEPTION · Requirements Analysis · 2026-09-07

Greenfield 멀티테넌트 복잡도: 중~복잡 MVP / 로컬 데모

1. 개요

디지털 주문 시스템으로 고객에게는 대기 없는 즉시 주문 경험을, 매장 운영자에게는 실시간 주문 관리와 운영 효율을 제공하는 멀티테넌트 테이블오더 플랫폼. 고객용 웹 UI · 관리자용 웹 UI · 백엔드 서버 · 데이터 저장소로 구성.

2. 기술 스택 & 범위 결정

멀티테넌시다중 매장 (매장 식별자로 데이터 격리)
백엔드Python (FastAPI)
프론트엔드React (Vite + React)
데이터베이스관계형 DB (PostgreSQL 계열 권장)
배포 환경로컬 개발 위주 (docker-compose, 데모/학습)
예상 규모소규모 (매장당 수~수십 테이블)
메뉴 이미지외부 URL 방식 (업로드/리사이징 없음)
고객 실시간 주문상태포함 (SSE)

3. 기능 요구사항

👤 고객용 (Customer)

  • FR-C1 테이블 태블릿 자동 로그인 & 세션 관리
  • FR-C2 메뉴 조회/탐색 (카테고리, 카드 UI, 44px+ 터치)
  • FR-C3 장바구니 (로컬 저장, 실시간 총액)
  • FR-C4 주문 생성 (주문번호 표시 → 자동 리다이렉트)
  • FR-C5 현재 세션 주문 내역 조회 (실시간 SSE)

🛠️ 관리자용 (Admin)

  • FR-A1 매장 인증 (JWT 16h, bcrypt, 시도 제한)
  • FR-A2 실시간 주문 모니터링 (그리드 + SSE, 2초 이내)
  • FR-A3 테이블 관리 (초기 설정/주문 삭제/이용 완료→이력/과거 내역)
  • FR-A4 메뉴 관리 (등록/수정/삭제/순서, 검증)

🔗 멀티테넌시

  • FR-MT1 모든 데이터(매장/메뉴/주문/이력/세션)를 매장 식별자로 격리
  • FR-MT2 요청은 자신의 매장 범위 데이터에만 접근 (테넌트/테이블 소유권 검증, IDOR 방지)

4. 비기능 요구사항 & 활성 확장

적용 🔒 Security Baseline (SECURITY-01~15)
  • bcrypt 해싱, JWT 서버측 검증, 브루트포스 방지, 쿠키 Secure/HttpOnly/SameSite
  • 입력 검증 · 파라미터라이즈드 쿼리 (SQL 인젝션/XSS 방지)
  • 객체 수준 인가(IDOR 방지) · CORS 화이트리스트 · 보안 헤더(CSP/HSTS 등)
  • 구조적 로깅(민감정보 제외) · 의존성 잠금/취약점 스캔 · fail-closed 에러 처리
적용 🛡️ Resiliency Baseline (RESILIENCY-01~15)
  • DR 전략: Backup & Restore (RTO/RPO 시간 단위)
  • 헬스 체크(딥 헬스체크 for DB) · 외부 호출 타임아웃 · 그레이스풀 디그레이드
  • 자동 백업(암호화·보존 정책) · 메트릭/로그 관측성 · 대시보드
  • 변경관리/인시던트 대응: 기존 조직 프로세스 사용 (추후 참조 제공)
  • 이연 CI/CD·롤백·리전 토폴로지·복원력 테스트 → NFR Design 단계
적용 🧪 Property-Based Testing (PBT-01~10)
  • 프레임워크: Hypothesis (Python)
  • 속성 식별(라운드트립·불변식·멱등성·상태 기반) → 설계 산출물 반영
  • 불변식 예: 총액 = Σ(단가×수량), 세션 종료 후 현재 총액 = 0
  • 상태 기반 PBT: 장바구니, 테이블 세션/주문 파이프라인
  • 예제 기반 테스트와 병행 (크리티컬 경로는 양쪽 모두)

⚡ 성능

  • NFR-P1 신규 주문 관리자 화면 2초 이내 표시(SSE)
  • NFR-P2 소규모(데모/MVP) 트래픽 기준 응답성

5. 핵심 데이터 개체 (초안)

Store 매장 Menu 메뉴 Table 테이블 TableSession 세션 Order 주문 OrderHistory 이력

세션 라이프사이클(첫 주문 시작 → 주문 누적 → 이용 완료 → 이력 이동/총액 리셋)이 도메인의 핵심. 상세 스키마는 Application/Functional Design 단계에서 구체화.

6. 구현 제외 (Constraints)

  • 결제: 실제 결제/PG 연동/영수증/환불/포인트·쿠폰
  • 인증: OAuth·SNS 로그인, 2FA/OTP (관리자 JWT/bcrypt 기본 인증은 포함)
  • 파일/컨텐츠: 이미지 리사이징/최적화, CMS, 광고 (이미지는 URL 참조만)
  • 알림: 푸시/SMS/이메일/소리·진동
  • 주방: 주방 전달, 식재료 재고 관리
  • 고급 기능: 매출 분석/리포트, 재고 관리, 직원/권한, 예약, 리뷰, 다국어
  • 외부 연동: 배달 플랫폼, POS, SNS 공유, 지도/번역 API

※ 확장이 요구하는 운영 로깅/모니터링은 위 "매출 분석 제외"와 상충하지 않음(운영 관측성 vs 비즈니스 분석).

7. 범위 주의사항

⚠️ 비차단(Non-blocking) 긴장: 로컬 데모/MVP 범위(소규모·docker-compose)와 프로덕션 수준 확장 3종 전면 적용은 약한 긴장 관계에 있습니다. 논리적 모순은 아니며(학습/워크숍 맥락에서 완전한 엔지니어링 엄격성 적용은 타당), 사용자의 명시적 지시("모두 A")에 따라 진행합니다. 실무적 함의: 로컬 데모임에도 암호화·입력검증·구조적 로깅·PBT·백업/복구 설계가 요구되어 구현 범위가 단순 CRUD보다 커집니다.
