# Menu — Business Rules (U3)

**단위**: U3 menu | **스토리**: US-MENU-01~07
불변식 중 **BR-M15~M18**은 Property-Based Testing(Hypothesis) 대상입니다. [PBT]

---

## 검증 규칙 (SEC-05)
- **BR-M01**: `name`은 필수, 1~100자. 공백만은 불가(trim 후 길이 검사).
- **BR-M02**: `price`는 정수이며 ≥ 0 (KRW). 음수·소수·비정수 → 422.
- **BR-M03**: `category`는 필수, 1~50자.
- **BR-M04**: `description`은 선택, ≤500자.
- **BR-M05**: `image_url`은 선택, ≤500자, `http://`|`https://`로 시작. 형식만 검증(도달성 검사 안 함).
- **BR-M06**: 등록(POST)과 수정(PUT)은 동일한 검증 규칙을 적용한다.

## 테넌트 격리 / 권한 (SEC-08 IDOR 방지)
- **BR-M07**: 모든 조회·쓰기는 컨텍스트 `store_id`로 스코프된다. 타 매장 메뉴는 존재하지 않는 것처럼 취급(404, 존재 미노출).
- **BR-M08**: 조회(GET 목록/단건)는 `require_customer`(활성 세션) 또는 `require_admin`에게 허용. 쓰기(POST/PUT/DELETE/reorder)는 `require_admin` 전용(그 외 403/401).
- **BR-M09**: 리포지토리(`TenantScopedRepository`) + 서비스 계층에서 소유권을 이중 확인한다(단일 방어에 의존하지 않음).

## 소프트 삭제
- **BR-M10**: 삭제는 `deleted_at` 설정(소프트). 삭제된 메뉴는 고객·관리자 모든 조회에서 제외된다.
- **BR-M11**: 삭제는 과거 주문 이력에 영향을 주지 않는다(주문의 메뉴명·단가는 U4 items 스냅샷으로 보존).
- **BR-M12**: 이미 삭제된 메뉴를 다시 삭제/수정 시도 → 404.

## 노출 순서 (US-MENU-07)
- **BR-M13**: 등록 시 `display_order` 미지정이면 `max(store 내 display_order)+1`을 부여(항상 뒤에 추가).
- **BR-M14**: 재정렬은 원자적이다 — 요청 `menu_ids`가 자기 매장 미삭제 메뉴 집합과 정확히 일치해야 한다(누락·외부·중복 시 422, 부분 반영 없음).

## 불변식 (PBT 대상)
- **BR-M15**: **테넌트 격리** — 임의의 매장 A·B와 임의 메뉴 집합에 대해, A 컨텍스트의 목록/단건 조회는 절대 B의 메뉴를 반환하지 않는다. (PBT-03)
- **BR-M16**: **재정렬 순열 보존** — 재정렬 입력이 현재 메뉴 id의 순열이면, 재정렬 후 `display_order` ASC 정렬 결과의 id 순서가 입력 순서와 정확히 일치하고 메뉴 집합(개수·id)은 불변이다.
- **BR-M17**: **소프트삭제 단조성** — 삭제 후 목록 크기는 정확히 1 감소하고, 삭제된 id는 이후 어떤 조회에도 나타나지 않으며, 남은 메뉴는 변하지 않는다.
- **BR-M18**: **가격 왕복** — 검증을 통과한 임의의 유효 price(≥0 정수)는 생성·조회 왕복에서 값이 보존된다(형 변환/반올림 손실 없음).

## 응답/그룹핑
- **BR-M19**: 고객 목록은 카테고리별 그룹, 그룹 내 `display_order` ASC(동순위 name ASC), 그룹 순서는 각 카테고리 최소 display_order ASC(동순위 카테고리명 ASC)로 결정적이다.
- **BR-M20**: 오류는 U1 중앙 핸들러를 통해 일반화 메시지 + correlation_id로 반환된다(fail-closed, SEC-15).
